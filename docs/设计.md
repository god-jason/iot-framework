建议将这套软件设计成一个独立的 STM32 通用嵌入式 IoT Framework，而不是针对某一款产品开发一套程序。

你的应用场景虽然不同，但底层需求高度相似：

- IO 控制板：GPIO、ADC、PWM、定时器、继电器、通信。
- 智能家居：设备管理、传感器、执行器、网络通信、自动化。
- 饲料投喂机器人：电机控制、重量检测、运动控制、状态机、任务调度。
- 智能玩具：音频、灯光、电机、传感器、交互逻辑。
- 远程设备：ML307 4G、MQTT、远程控制、OTA、设备日志。

我建议采用 分层架构 + 组件化 + 事件驱动 + 状态机 + 统一硬件抽象层。

最重要的设计原则是：

1. 算法库、数据结构、工具库不依赖 STM32 HAL。
2. 硬件驱动通过统一接口封装，兼容 STM32F103、STM32F407。
3. ML307 作为独立通信组件，不与业务逻辑耦合。
4. 所有功能模块支持独立启用和裁剪，适应不同 Flash/RAM 容量。
5. 尽量不使用动态内存，支持静态内存池。
6. 同一套业务代码可以在 F103、F407 甚至 Linux 主机上进行测试。

# 三、Bootloader 和升级系统

这是整个框架最重要的基础设施之一。

## 3.1 Bootloader 功能设计

建议把升级分成四个层次：

| 层次                | 功能                  |
| ----------------- | ------------------- |
| Bootloader        | 引导、校验、启动、回滚         |
| Upgrade Manager   | 升级流程管理              |
| Upgrade Transport | UART、4G、USB、CAN 等传输 |
| Image Manager     | 固件分区、版本、完整性验证       |

建议的 API：

```
typedef enum {
    BOOT_MODE_NORMAL,
    BOOT_MODE_UPGRADE,
    BOOT_MODE_RECOVERY,
    BOOT_MODE_ROLLBACK
} boot_mode_t;

typedef enum {
    UPGRADE_IDLE,
    UPGRADE_PREPARE,
    UPGRADE_RECEIVING,
    UPGRADE_VERIFYING,
    UPGRADE_READY,
    UPGRADE_INSTALLING,
    UPGRADE_SUCCESS,
    UPGRADE_FAILED
} upgrade_state_t;

typedef struct {
    uint32_t version;
    uint32_t size;
    uint32_t crc32;
    uint32_t image_addr;
    uint32_t image_type;
} firmware_info_t;

typedef struct {
    upgrade_state_t state;
    uint32_t total_size;
    uint32_t received_size;
    uint32_t current_offset;
    int error;
} upgrade_context_t;
```

核心接口：

```

```

## 3.2 升级方式

## 统一升级流程

升级请求

串口 / 4G / USB / CAN

Upgrade Manager

接收、断点续传、进度管理

固件存储区

临时区 / OTA 分区 / 外部 SPI Flash

固件验证

CRC32 / SHA256 / 数字签名 / 版本检查

Bootloader 安装和启动

启动确认 / 看门狗 / 失败回滚

升级传输层建议支持：

- UART X/YMODEM：现场串口升级。
- 自定义 UART 协议：方便配合上位机升级。
- HTTP/HTTPS：ML307 下载固件。
- MQTT：接收升级通知、版本、下载地址。
- USB DFU：后续扩展。
- CAN：工业设备扩展。

特别建议：

不要让 Bootloader 直接承担完整的 ML307 AT 通信和 HTTP 下载功能。

更合理的方式是：

1. APP 通过 ML307 获取升级文件。
2. APP 将固件下载到外部 Flash 暂存区，或合适的内部升级区。
3. APP 验证文件并写入升级请求标志。
4. 重启进入 Bootloader。
5. Bootloader 独立完成固件安装、校验和启动。

这样 Bootloader 代码可以保持非常精简。

### 3.3 STM32F103/F407 分区策略

这两款 MCU 的 Flash 容量存在很大差异，因此不能采用完全相同的分区方案。

| 项目         | STM32F103       | STM32F407       |
| ---------- | --------------- | --------------- |
| Bootloader | 内部 Flash        | 内部 Flash        |
| APP        | 内部 Flash        | 内部 Flash        |
| OTA 暂存     | 外部 SPI Flash 推荐 | 外部 SPI Flash 推荐 |
| 双镜像        | 视 Flash 容量      | 视 Flash 容量      |
| 回滚         | 需要暂存镜像或备份       | 可设计双镜像          |

建议外部 Flash 采用统一存储抽象：

```
typedef struct {
    int (*init)(void);
    int (*read)(uint32_t addr, void *buf, uint32_t len);
    int (*write)(uint32_t addr, const void *buf, uint32_t len);
    int (*erase)(uint32_t addr, uint32_t len);
    uint32_t (*size)(void);
} flash_ops_t;
```

不要只依赖 CRC32。CRC 用于传输错误检测，而固件安全性应通过 SHA-256 和数字签名验证。还要处理掉电恢复、升级中断、固件防降级和 APP 启动确认。

## 4.1 滤波器 Filter

这是物联网设备中使用频率非常高的一部分。

| 算法         | 用途          | 推荐程度 |
| ---------- | ----------- | ---- |
| 均值滤波       | ADC、称重      | 必须   |
| 滑动平均       | 温度、压力       | 必须   |
| 中值滤波       | 去除脉冲干扰      | 必须   |
| 限幅滤波       | 异常值剔除       | 必须   |
| 一阶低通       | 温度、电压       | 必须   |
| 一阶高通       | 信号变化检测      | 推荐   |
| 指数移动平均 EMA | 传感器数据平滑     | 必须   |
| 卡尔曼滤波      | 位置、速度、传感器融合 | 推荐   |
| 扩展卡尔曼 EKF  | 非线性系统       | 可选   |
| 互补滤波       | IMU 姿态      | 推荐   |
| FIR        | 数字信号处理      | 推荐   |
| IIR        | 信号滤波        | 推荐   |
| 滞回滤波       | 开关量、阈值检测    | 必须   |
| 滤波器组       | 多传感器处理      | 可选   |

建议接口统一：

```
typedef struct {
    float input;
    float output;
    float state;
} filter_t;

void filter_mean_init(filter_t *f, float *buffer, uint16_t size);
float filter_mean_update(filter_t *f, float input);

void filter_median_init(filter_t *f, float *buffer, uint16_t size);
float filter_median_update(filter_t *f, float input);

void filter_ema_init(filter_t *f, float alpha);

void filter_lowpass_init(filter_t *f, float cutoff, float sample_rate);
float filter_lowpass_update(filter_t *f, float input);
```

实际开发中，不建议所有滤波器共用一个 `filter_t`。可以统一初始化、更新接口风格，但各滤波器应有自己的上下文结构体。

# 五、校验算法 Checksum / Crypto

建议将数据完整性校验和密码学算法分开。

| 分类   | 算法           | 用途       |
| ---- | ------------ | -------- |
| 简单校验 | SUM8、SUM16   | 简单数据包    |
| 异或   | XOR8、XOR16   | 串口协议     |
| CRC  | CRC8         | 传感器      |
| CRC  | CRC16/MODBUS | Modbus   |
| CRC  | CRC16/CCITT  | 通信协议     |
| CRC  | CRC32        | 固件、文件    |
| Hash | MD5          | 旧协议兼容    |
| Hash | SHA1         | 兼容性      |
| Hash | SHA256       | 固件完整性    |
| MAC  | HMAC-SHA256  | 消息认证     |
| 加密   | AES-128/256  | 数据加密     |
| 签名   | ECDSA        | OTA 固件签名 |

建议 API：

```
uint8_t crc8(const void *data, uint32_t len);

uint16_t crc16_ccitt(const void *data, uint32_t len);

void sha256_init(void *ctx);
void sha256_update(void *ctx, const void *data, uint32_t len);
void sha256_final(void *ctx, uint8_t digest[32]);
```

建议不要自己实现密码学核心算法后直接用于量产。可以考虑移植成熟的 Mbed TLS、TinyCrypt 等经过广泛使用的实现。

# 十一、AT 指令引擎

这一部分建议重点设计。不要直接在 ML307 驱动中通过 `HAL_UART_Transmit()` 发送命令，再通过 `strstr()` 判断响应。

应该实现一个独立的 AT Engine，所有 AT 模组都可以复用。

## 11.1 AT 引擎架构

AT Command API

at_send · at_query · at_exec

AT Transaction Manager

命令队列 · 超时 · 重试 · 响应匹配

Response Parser

OK / ERROR / 响应数据

URC Parser

异步主动上报

UART Transport

DMA · RingBuffer · Idle 中断 · 发送接口

## 11.2 AT 基础结构体

```
typedef enum {
    AT_RESULT_OK,
    AT_RESULT_ERROR,
    AT_RESULT_TIMEOUT,
    AT_RESULT_BUSY,
    AT_RESULT_CANCEL,
    AT_RESULT_OVERFLOW
} at_result_t;

typedef enum {
    AT_STATE_IDLE,
    AT_STATE_SENDING,
    AT_STATE_WAITING,
    AT_STATE_RECEIVING,
    AT_STATE_COMPLETE,
    AT_STATE_ERROR
} at_state_t;

typedef struct {
    const char *command;
    const char *expect;
    uint32_t timeout;
    uint8_t retry;
} at_command_t;

typedef struct {
    at_state_t state;
    at_result_t result;

    const char *response;
    uint16_t response_len;

    uint32_t timeout;
    uint8_t retry;

    void (*callback)(at_result_t result,
                     const char *response,
                     uint16_t len,
                     void *user);

    void *user;
} at_request_t;
```

## 11.3 AT 核心 API

```
int at_init(void);
int at_start(void);
int at_stop(void);

int at_send(const char *cmd);
int at_query(const char *cmd, at_request_t *req);
int at_exec(const char *cmd, uint32_t timeout);

int at_register_urc(const char *prefix,
                    at_urc_callback_t callback);

int at_unregister_urc(const char *prefix);

void at_input(const uint8_t *data, uint16_t len);
void at_process(void);

int at_is_busy(void);
void at_abort(void);
```

## 11.4 必须处理的特殊情况

AT 引擎不能简单地把每个换行符当作一个完整响应。

需要考虑：

1. 一条响应分多次 UART DMA 接收。
2. 一次 DMA 接收到多条响应。
3. `OK` 和 `ERROR` 结束标志。
4. `+xxx:` 类型的数据响应。
5. URC 异步主动上报。
6. 命令执行超时。
7. 命令重试。
8. 模组主动重启。
9. 串口接收溢出。
10. 数据模式和命令模式切换。
11. `>` 提示符。
12. 二进制数据和文本混合传输。
13. 响应内容中出现 `OK` 字符串。
14. 上一条命令未完成时不能错误匹配下一条命令的响应。

特别是第 13、14 点：建议使用 AT 协议解析器进行行边界和终止标记识别，不要只使用字符串查找。

建议 AT 引擎只允许一条普通命令处于等待响应状态。URC 单独分发。对于 HTTP、MQTT 等数据发送过程，应增加专门的多阶段事务处理机制。

# 十四、HAL 硬件抽象层

这一层决定框架未来能否轻松适配不同 MCU。

建议所有硬件驱动统一采用 `ops + context` 设计。

例如 UART：

```
typedef struct {
    int (*init)(void *ctx);
    int (*deinit)(void *ctx);

    int (*send)(void *ctx,
                const uint8_t *data,
                uint16_t len);

    int (*receive)(void *ctx,
                   uint8_t *data,
                   uint16_t len);

    int (*set_baudrate)(void *ctx, uint32_t baudrate);

    void *ctx;
} uart_ops_t;
```

上层 AT 引擎只依赖 `uart_ops_t`，完全不需要知道使用的是 USART1 还是 USART2。

HAL 建议包含：

| 驱动    | 功能          |
| ----- | ----------- |
| GPIO  | 输入、输出、中断    |
| UART  | 中断、DMA、空闲中断 |
| SPI   | 阻塞、中断、DMA   |
| I2C   | 读写、设备扫描     |
| ADC   | 单次、DMA、连续采样 |
| PWM   | 频率、占空比      |
| TIMER | 定时器         |
| DMA   | 数据传输        |
| FLASH | 擦除、读写       |
| RTC   | 日期时间        |
| WDG   | 独立看门狗       |
| EXTI  | 外部中断        |

对于 STM32F103/F407，我建议：

- HAL 层使用 ST HAL 或 LL。
- 框架层不直接调用 HAL。
- 中断中只做数据搬运和事件通知。
- 复杂逻辑放到任务上下文执行。
- UART 优先使用 DMA + RingBuffer。
- 不要在中断中执行 JSON、MQTT、AT 解析。

# 十五、框架开发规范

这部分很容易被忽略，但会直接影响以后维护成本。

## 15.4 内存管理

我特别建议针对 STM32F103 做内存优化：

- 优先静态分配。
- 尽量使用固定大小内存池。
- 避免频繁 `malloc/free`。
- JSON 使用固定解析缓冲区。
- MQTT 使用固定消息缓冲区。
- UART 使用静态环形缓冲区。
- 避免大数组放在栈上。
- 大型算法支持按需编译。

# 十六、建议的开发优先级

不要一开始就把所有模块全部实现。应该先构建一个可靠的核心，再逐步扩展。

1. 第一阶段：基础核心

   最高优先级

   - crc8、crc16、crc32
   - hex、base64、bcd

   - HAL GPIO、UART、SPI、I2C
   - ADC、PWM、DMA、Flash

   - Timer、Scheduler

# 十七、针对 F103 和 F407 的不同配置

建议不要维护两套框架，而是维护一套源码、两套平台配置。

| 配置   | STM32F103            | STM32F407    |
| ---- | -------------------- | ------------ |
| 算法   | 基础算法、定点优先            | 完整算法、浮点优先    |
| JSON | jsmn                 | cJSON 或 jsmn |
| 内存   | 静态内存池                | 静态池 + 可选动态内存 |
| 调度   | Baremetal / FreeRTOS | FreeRTOS     |
| MQTT | 轻量级                  | 完整功能         |
| OTA  | 外部 Flash 暂存          | 外部 Flash 暂存  |
| 加密   | 精简密码库                | 完整密码库        |
| 行为树  | 按需启用                 | 完整功能         |

还有一点：STM32F407 有硬件 FPU，而 STM32F103 没有。因此算法库最好同时考虑：

```
algorithm/
├── fixed/       # 定点实现
├── float/       # 浮点实现
└── common/      # 通用算法

# IoT-OS：通用嵌入式 IoT + RobotOS 框架

设计目标：

- 纯 C 语言，采用 C99 标准。
- 不依赖 STM32 HAL、LL。
- 不依赖任何特定 RTOS。
- 支持 STM32F103、STM32F407，也支持其他 MCU。
- 支持裸机、FreeRTOS、其他 RTOS。
- 支持 ML307、EC801 等 AT 通信模组。
- 核心库不依赖硬件。
- 默认静态内存管理。
- 支持功能裁剪。
- 模块之间通过接口、事件和回调解耦。

这次我会把接口设计到结构体、函数、回调、参数和模块职责的层面，作为后续编写完整 `.h/.c` 的依据。

# 一、首先确定整体设计原则

我建议把整个系统分成四层：

Application / RobotOS

产品应用、设备控制、业务流程、机器人任务、自动化

Components / Services

ML307、MQTT、HTTP、传感器、电机、设备管理、OTA

Core / Libraries

FSM、Event、Scheduler、Algorithm、Container、Utils、JSON

Port / Platform Interface

UART、GPIO、SPI、I2C、Flash、Tick、Mutex、Thread、Critical Section

这里特别强调：

不使用 HAL，不代表不需要硬件抽象。

我们自己定义一套与芯片无关的 `port` 接口。将来无论底层是直接操作寄存器、使用厂商 SDK，还是 Linux，都由对应的 Port 实现。

```

                        uint32_t len);

AT Engine 必须保证：

- 一般 AT 命令串行执行。
- URC 不占用普通命令事务。
- 每条命令有独立超时。
- 支持 `>` 等非换行提示符。
- 支持固定长度二进制数据。
- 不能将数据内容中的 `OK` 误判为命令结束。
- 支持接收缓冲区溢出检测。
- 支持模组重启后重新同步。

特别是二进制模式，建议采用显式状态切换，不要继续使用普通行解析器解析二进制内容。

## 14.1 状态机结构

```
typedef struct iot_fsm iot_fsm_t;
typedef struct iot_fsm_state iot_fsm_state_t;

typedef void (*iot_fsm_entry_fn)(
    iot_fsm_t *fsm,
    void *ctx
);

typedef void (*iot_fsm_action_fn)(
    iot_fsm_t *fsm,
    void *ctx,
    uint32_t event,
    void *data
);

typedef void (*iot_fsm_exit_fn)(
    iot_fsm_t *fsm,
    void *ctx
);

typedef bool (*iot_fsm_guard_fn)(
    iot_fsm_t *fsm,
    void *ctx,
    uint32_t event,
    void *data
);

struct iot_fsm_state {
    uint32_t id;

    iot_fsm_entry_fn entry;
    iot_fsm_action_fn action;
    iot_fsm_exit_fn exit;

    void *ctx;
};

typedef struct {
    uint32_t from;
    uint32_t event;
    uint32_t to;

    iot_fsm_guard_fn guard;
} iot_fsm_transition_t;

struct iot_fsm {
    const iot_fsm_state_t *states;
    uint16_t state_count;

    const iot_fsm_transition_t *transitions;
    uint16_t transition_count;

    const iot_fsm_state_t *current;

    void *ctx;

    bool running;
    bool paused;
};
```

## 14.2 FSM 接口

```
int iot_fsm_init(iot_fsm_t *fsm,
                 const iot_fsm_state_t *states,
                 uint16_t state_count,
                 const iot_fsm_transition_t *transitions,
                 uint16_t transition_count,
                 void *ctx);

int iot_fsm_start(iot_fsm_t *fsm, uint32_t initial_state);

int iot_fsm_stop(iot_fsm_t *fsm);

int iot_fsm_pause(iot_fsm_t *fsm);
int iot_fsm_resume(iot_fsm_t *fsm);

int iot_fsm_dispatch(iot_fsm_t *fsm,
                     uint32_t event,
                     void *data);

int iot_fsm_transition(iot_fsm_t *fsm,
                       uint32_t state_id);

uint32_t iot_fsm_get_state(const iot_fsm_t *fsm);

bool iot_fsm_is_state(const iot_fsm_t *fsm,
                      uint32_t state_id);

bool iot_fsm_is_running(const iot_fsm_t *fsm);
```

事件由调用者直接传入，FSM 不保存事件、不创建事件队列。

状态切换过程：

```
收到事件
   ↓
执行当前状态 action
   ↓
查找对应转换规则
   ↓
判断 guard
   ↓
当前状态 exit
   ↓
切换状态
   ↓
新状态 entry
```

建议额外支持状态机运行回调、状态转换通知，但不建议一开始就做复杂的层级 FSM。

# 二十二、正式实现前需要确定的几个接口原则

我建议以下设计决策作为整个框架的约束：

| 项目        | 最终建议                                     |
| --------- | ---------------------------------------- |
| C 标准      | C99                                      |
| 硬件依赖      | 不依赖 HAL                                  |
| OS 依赖     | 通过 Port 抽象                               |
| 内存        | 默认静态内存                                   |
| FSM       | 不内置事件队列                                  |
| Event     | 支持同步和异步分发                                |
| Scheduler | 独立于 RTOS                                 |
| 组件        | 统一生命周期                                   |
| 驱动        | ops + context                            |
| AT        | 独立事务引擎                                   |
| JSON      | Tokenizer + Writer                       |
| OTA       | Transport + Upgrade Manager + Bootloader |
| 算法        | 独立、可裁剪                                   |
| 测试        | 支持 PC Host 单元测试                          |

还有三点需要特别修正：

1. 前面基础类型代码中的 `#define IOT_ERR_CANCEL -16;`，正式版本应写成 `#define IOT_ERR_CANCEL (-16)`。
2. RingBuffer、Event、AT 等跨中断和任务使用的模块，需要明确并发模型及同步策略。
3. Bootloader 的 Flash 写入、向量表切换、栈指针设置、跳转入口等属于平台相关实现，不能伪装成完全通用的 C 实现。

# 二十三、建议的实际落地顺序

虽然接口目录已经覆盖了整套框架，但我不建议直接一次性写完所有代码。

建议按照以下依赖关系开发：

## 第一批：基础库

先完成

`iot_types` → `iot_error` → `iot_port` → `iot_os`

`memory` → `list` → `queue` → `ringbuf` → `pool`

`bytes` → `string` → `hex` → `base64` → `bcd` → `crc`

`datetime` → `logger` → `event`

## 第二批：运行框架

`timer` → `scheduler` → `component` → `service` → `device`

`fsm` → `action` → `behavior` → `planner` → `executor`

## 第三批：通信系统

`uart port` → `ringbuf` → `at parser` → `at engine`

`ml307` → `network` → `mqtt` → `http`

## 第四批：系统能力

`storage` → `kv` → `bootloader` → `upgrade`

`json` → `modbus` → `diagnostics` → `shell`

## 第五批：机器人能力

`filter` → `statistics` → `pid` → `motion`

`sensor` → `motor` → `robot application`
